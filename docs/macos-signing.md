# Stable local signing for Moss Display

Moss Display keeps its bundle ID `org.moss.usb-display` and is signed with an
Apple-issued code-signing identity held in the login Keychain. The build never
falls back to an ad-hoc signature. No private key is copied into the repository,
and the normal local build does not upload the app. The separate trusted-main
release workflow signs and notarizes using encrypted GitHub Actions secrets;
see [release setup](releases.md).

Configure once on each development Mac:

```sh
scripts/configure-display-signing.sh
scripts/build-display-host.sh
```

Setup prefers a single valid **Developer ID Application** identity. If none is
available, it accepts a single **Apple Development** identity. When there are
multiple candidates, select explicitly using the public fingerprint:

```sh
security find-identity -v -p codesigning
scripts/configure-display-signing.sh <SHA-1-fingerprint>
```

The selected fingerprint is stored in the ignored `.cache/macos-signing-identity`
file. `scripts/configure-display-signing.sh --check` validates it without changing
the app or Keychain. Builds need normal Keychain access; the coding sandbox can
report zero identities even when the login Keychain has valid certificates.
macOS may ask the user to allow `codesign` to use the selected private key. Enter
any Keychain password only into the native macOS dialog. Signing also requests
Apple's secure timestamp, so internet access is needed.

If no Apple identity is installed, add the developer account in Xcode Settings
→ Accounts and use **Manage Certificates**. Apple documents this workflow in
[Synchronizing code signing identities](https://developer.apple.com/documentation/xcode/sharing-your-teams-signing-certificates).
Local setup does not create certificates or change Keychain trust. The release
job imports only its configured identity into a temporary runner Keychain, then
deletes it. CI test builds explicitly use `--unsigned`; missing release
credentials never silently downgrade a signed release.

## Why rebuilds can keep permission

The previous ad-hoc build was identified by its changing code hash. Apple-signed
builds use the normal designated requirement generated by `codesign`, which
binds the app identifier to Apple's certificate chain and the signing team.
Future builds under the same certificate class and team can satisfy the same
requirement even when their executable bytes change. Apple describes how macOS
uses this identity to recognize privacy-authorized app updates in
[TN3127: Inside Code Signing: Requirements](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements).

The first transition from ad-hoc signing changes the identity, so one final
Screen Recording approval may be necessary. Remove the old Moss Display entry
in System Settings → Privacy & Security → Screen & System Audio Recording,
add the current `build/macos/Moss Display.app`, enable it, relaunch, and choose
Display on the device again. Keep the app at the same location. The scripts
never alter the privacy database or grant permission automatically.

Do not switch between Developer ID and Apple Development certificates or teams
between builds: their default designated requirements differ. When renewing a
certificate, configure the new fingerprint from the same class and team. Retain
the bundle ID. Stable signing addresses rebuild-induced identity changes;
macOS can still show consent or reminders under its own privacy policies.

Inspect the final app without changing it:

```sh
codesign --verify --deep --strict "build/macos/Moss Display.app"
codesign --display --verbose=4 "build/macos/Moss Display.app"
codesign --display -r- "build/macos/Moss Display.app"
```

The designated requirement should include `anchor apple generic`, the bundle
identifier, and a certificate condition tied to the signing team. An
identifier-only custom requirement would permit impersonation and is not used.

## Testing builds from a worktree

A worktree build is a staging artifact. Do not launch its `.app` from the
worktree: keep the already-authorized app at its established installation path.
Quit the running app, retain a rollback copy, and copy the fully tested signed
bundle into that same location. Verify with `codesign --verify --deep --strict`
and compare its designated requirement to the prior bundle before launching.
Changing build directories must not change the user-facing launch path. Do not
reset TCC or modify privacy grants as part of a normal update.
